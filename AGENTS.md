# Правила работы над «Мойдодыром»

Эти инструкции действуют для всего репозитория.

## Рабочий процесс

- Работаем без BMAD вообще: не активировать BMAD-навыки, агентов и процессы, не запускать его скрипты, не создавать `_bmad` и связанные служебные документы. Это относится и к обновлению этого файла.
- Выполнять задачи напрямую средствами проекта. Не добавлять методологии и обязательные этапы согласования без запроса пользователя.
- Общаться с пользователем и писать клиентские тексты на русском. Сохранять файлы в UTF-8.
- Вносить изменения в пределах задачи; не смешивать их с посторонним рефакторингом.

## Ориентиры в коде

- `main.py` → `moydodyr/app.py`: запуск бота, подключение роутеров и фоновой доставки.
- `moydodyr/bot/handlers/`: сценарии клиента и менеджеров; `customer.py` собирает клиентские роутеры. Сохранять fallback последним, чтобы он не перехватывал другие обработчики.
- `moydodyr/bot/states.py`, `keyboards.py`, `formatting.py`: состояния диалога, кнопки и карточки заявок.
- `moydodyr/domain.py`: валидация ввода, каталог и предварительная стоимость.
- `moydodyr/db.py`, `schema.sql`: доступ к PostgreSQL, FSM, заявки, история и outbox.
- `moydodyr/bot/services/outbox.py`, `moydodyr/integrations/n8n.py`: доставка уведомлений и лидов.
- `README.md`: инструкция запуска и команды администратора. При изменении поведения обновлять соответствующий раздел.

## Запуск и проверка

- Python 3.12+; зависимости устанавливать через `uv sync --locked`. При изменении зависимостей обновлять `pyproject.toml` и `uv.lock` совместно через uv.
- PostgreSQL запускать из корня: `docker compose up -d --wait`. Compose запускает только БД; бот запускается отдельно: `uv run python main.py`.
- Конфигурация читается из `.env` через `Settings.load()` в `moydodyr/config.py`; образец переменных — `.env.example`.
- Перед запуском или перезапуском проверять существующие процессы этого проекта. Для одного токена должен работать один polling-экземпляр; останавливать только относящиеся к этому боту процессы.
- При фоновом запуске в Windows использовать скрытое окно и перенаправлять вывод в `logs/`. Проверять старт polling и ошибки в журнале, а не только наличие PID.
- Проверка Python-кода: `uv run ruff check .`; форматирования: `uv run ruff format --check .`.
- Тесты находятся в `tests/`. Для новой логики добавлять содержательные тесты и запускать их через `uv run pytest`; отсутствие тестов не считать успешным прогоном.
- Для изменений документации достаточно проверить содержание, пути и diff. В отчёте указывать, что действительно проверено.

## Данные и бизнес-правила

- Сохранять заявки и связанные уведомления в одной транзакции через `Database.submit()`; обращения к менеджеру — через `Database.enqueue_contact()`. Не заменять outbox прямой отправкой этих уведомлений из обработчиков.
- Сохранять защиту от повторной записи: уникальные `draft_id` заявок и `dedupe_key` уведомлений. Не обещать ровно одну внешнюю доставку: повторная отправка после сбоя возможна.
- Проверять права администратора при выполнении действий, включая callback-запросы. Переходы статусов и проверку ответственного менеджера сохранять в `Database.transition()` вместе с записью истории.
- Хранить FSM в PostgreSQL; изменения формата состояния и черновиков должны учитывать уже начатые диалоги.
- `catalog.json` используется для начальной загрузки. Действующий каталог хранится в `bot_settings`; правка JSON не обновляет существующую запись. Для изменений действующего каталога использовать предусмотренные команды администратора или явное обновление данных.
- Расчёт вести через `Decimal`, сохраняя округление вверх до целого рубля. При отсутствии нужных тарифов не подставлять нулевую стоимость.
- Даты клиента проверять относительно `Europe/Moscow`. Дата и время — пожелания, а не подтверждённое бронирование бригады.
- `schema.sql` выполняется при каждом подключении приложения: изменения должны быть повторно применимыми и сохранять существующие данные. Не сбрасывать БД и не удалять Docker volume для исправления схемы.

## Секреты и внешние интеграции

- Не коммитить `.env`, токены, пароли, секреты webhook, дампы БД и клиентские данные. В примерах использовать заглушки.
- Не выводить содержимое `.env`, строки подключения с паролем или тела запросов с секретами в журнал и ответы. Проверять наличие настроек без раскрытия значений.
- n8n требует одновременно HTTPS URL и секрет. Добавлять секрет только при отправке; не сохранять его в outbox.
- Сохранять контракт n8n: успех — HTTP 200 и `ok: true`, `lead_id` сохраняется для заявки; HTTP 401 — постоянная ошибка, временные сбои проходят через повторы outbox.
- Telegram использует HTML-разметку: экранировать пользовательский текст при включении в сообщения.
- Проверки не должны создавать реальные заявки, отправлять сообщения клиентам или вызывать рабочий webhook без соответствующей задачи. Использовать изолированную БД и подменённые внешние вызовы для автоматических тестов.
